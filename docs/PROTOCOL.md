# Протокол MDVR (видеодомофон 192.168.31.150:9000)

Документ — результат реверс-инжиниринга по дампам трафика (файлы
`fromServer720*.bin`). Все смещения и размеры выведены эмпирически
и проверены декодированием через FFmpeg.

## 1. Транспорт

- TCP, порт **9000**. Соединение инициирует клиент.
- Также открыт порт **8000** — отвечает `412 Precondition Failed` на любой HTTP
  (SDK-порт, назначение не выяснялось). RTSP (554), HTTP (80) закрыты.
- TTL пакета ~61 (несколько хопов); устройство отвечает на ICMP.

## 2. Handshake

Клиент отправляет бинарный запрос **500 байт** — файл `toServer720.bin`
(снят с оригинального приложения; имя «720» отсылает к запрошенному потоку).

Hex-значимые байты (весь остальной объём — нули):

```
0000: 00 00 00 01 00 00 00 03 03 00 00 00 ...
0010: ... 00 68 00 00 00 01 00 00 00 10 00 00 00 01 00 00 00 01 ...
0028: 00 d6 9b 05 00 00 00 00 50 31 e3 02 00 00 75 00 b8 d5 9b 05 1e 55 b3 77 ...
```

После handshake сервер отвечает заголовком сессии (~0x210 байт), в котором
опознаётся строка `MDVR96NT_2_R`, поля `40 1f 00 00` (=8000, порт?),
`14 96 00 00` (=38416). Далее без остановки идёт поток видео-пакетов.

**Примечание:** при каждом новом соединении сервер продолжает слать поток
без повторной аутентификации; handshake достаточно отправить один раз.

## 3. Заголовок сессии

```
0000: 10 00 00 00 00 00 00 00 00 00 00 03 01 00 00 13 ...
0034: 04 1a 0b 13 16 39 36 1a 0b 13 16 39 36          — серийные поля
0040: 01 00 00 00 01 00 00 01 08 00 00 00 ...
0050: 40 1f 00 00 ... 14 96 00 00
0060: "MDVR96NT_2_R"                                    — модель устройства
0199: ... 01 41 00 00 40 1f 00 00 ...
```

## 4. Формат видео-пакета

Пакеты обоих каналов чередуются в общем потоке. Граница пакета —
ASCII-маркер:

```
"NNdcH264"   (8 байт)
```

где `NN` — десятичный номер канала ASCII-цифрами: `00` или `01`.
Суффикс `dcH264` — от AVI-нотации (`00dc` = «stream 00, compressed»),
т.е. поток унаследован от файлового формата AVI.

### Заголовок пакета (после маркера)

| Смещение | Размер | Тип | Значение (эмпирически) |
|---|---|---|---|
| +0 | 8 | ASCII | `NNdcH264` |
| +8 | 4 | u32 LE | размер полезной нагрузки |
| +12 | 4 | u32 LE | флаги/счётчик (`04 03 00 00` у кадров с заголовками) |
| +16 | 8 | u64 LE | **µs-таймстамп** (монотонный, устройства) |
| +24 | ~14–32 | — | служебные поля, составляют до первого start code |

### Полезная нагрузка

После переменного служебного заголовка идёт **элементарный поток H.264
в формате Annex-B** (start codes `00 00 00 01`). Границу полезной нагрузки
надёжнее всего находить поиском первого start code после +24.

Пример первого пакета канала 00:

```
30 30 64 63 48 32 36 34   "00dcH264"
7f 40 00 00               размер 0x407f
10 00 00 00               флаги
95 45 e4 70 04 03 00 00   таймстамп (µs) LE → 0x0000_0304_70e4_4595
1a 0b 13 16 0c 16         служебное
00 00 19 00 00 00         25 (fps?), нули
c0 02 40 02               704×576 LE ← размеры кадра!
00 00 00 01 67 42 00 1e 95 a8 2c 04 99   SPS (Baseline)
00 00 00 01 68 ce 3c 80               PPS
00 00 00 01 06 e5 01 2b 80            SEI
00 00 00 01 65 ...                    IDR-кадр
```

Замечание: `c0 02` = 704, `40 02` = 576 (little-endian) в заголовке канала 00.

## 5. Каналы

| Канал | Маркер | Разрешение | Частота кадров | SPS/PPS | Статус |
|---|---|---|---|---|---|
| 00 | `00dcH264` | 704×576 | ~1.25 fps (медиана дельт 800 мс; встречаются 40–920 мс) | с каждым IDR | **декодируется, единственная реальная камера** |
| 01 | `01dcH264` | формально 720p | 25 fps (дельты 40 мс) | **не передаются вообще** | **не содержит изображения** (см. ниже) |

Таймстампы пакетов — микросекунды, монотонные, общие для каналов.
Пример дельт ch01 (мс): `40 40 39 40 41 38 39 40 …`

### 5.1. Канал 01: итог исследования (окончательный)

Канал 01 исследован исчерпывающе. **Вывод: он не содержит изображения
с подключённой вызывной панели.** Подтверждённая гипотеза: устройство
рассчитано на две вызывные панели, ch01 — вход второй, физически
не подключённой; её энкодер передаёт цифровой мусор. Доказательства:

1. **Родных SPS/PPS у канала 01 нет.** Проверено свежей TCP-сессией
   (захват с первого пакета): первый пакет `01dcH264` начинается
   с одиночного P-слайса (NAL type 1), заголовков множества устройство
   не шлёт ни в начале сессии, ни в заголовке сессии, ни между кадрами.
2. **Параметры слайсов восстановлены грид-поиском** (см. 5.2):
   1280×720, Baseline@L3.1, `frame_num` 8 бит, poc_type=2, GOP=20
   с intra-refresh (fn циклится 1..19, 122 сброса за 150-с захват —
   без единого IDR).
3. **Решающий эксперимент — сравнение со сценой камеры.** Серый IDR
   (битовая хирургия заголовка под наше пространство, см. 5.3) + 250
   живых P-слайсов → декод FFmpeg → корреляция даунскейл-кадра
   с эталонной сценой канала 00 из того же захвата:
   - PPS `68ce3880` (deblock=0): 508 ошибок, корреляция **+0.073**;
   - PPS `68ce3c80` (родной вид, deblock=1): 512 ошибок, корреляция **−0.199**;
   - PPS deblock=1 qp28: 512 ошибок, корреляция **−0.222**.
   Корреляция ≈ 0 при всех комбинациях = картинка не связана со сценой
   камеры. «Вертикальные разноцветные полосы» после concealment-декодирования
   и есть настоящее содержимое канала.
4. Косвенная проверка: кросс-корреляция рядов размеров кадров ch00↔ch01
   (движение в кадре одной камеры синхронно меняло бы битрейт) — слабая
   (0.37 на сглаженных), для одной камеры невероятно.

Практическое следствие: **«HD 1280×720» не является HD-версией камеры**.
Единственный источник видео — канал 00. Попытки декодировать ch01
«правильными» SPS/PPS бесперспективны — декодировать нечего.

### 5.2. Параметры потока канала 01 (для протокола)

Найдены грид-поиском по битстриму (min ошибок декодера), косвенно
подтверждаются структурой слайсов:

- SPS: `67 42 00 1f 95 a8 14 01 6e 40` — Baseline, Level 3.1,
  `log2_max_frame_num_minus4=4` (fn 8 бит), poc_type=2,
  max_num_ref_frames=1, gaps_in_frame_num=1, 80×45 MB = 1280×720;
- PPS: `68 ce 38 80` — CAVLC, `deblock_filter_control_present=0`,
  pic_init_qp=26 (родной PPS канала 00 `68ce3c80` имеет deblock=1 —
  вариант тоже проверен, результат идентичен);
- slice-заголовок P-слайса: `first_mb_in_slice ue(0), slice_type ue(0),
  pps_id ue(0), frame_num u(8), [poc_type=2 → без poc_lsb],
  num_ref_idx_active_override_flag u(1)=0, ref_pic_list_modification,
  qp_delta se(v)` — разбор воспроизводим парсером (`/tmp/opencode/pdump.py`
  в истории сессии).

### 5.3. Битовая хирургия IDR (отработанная техника)

Для старта декодирования P-only потока нужен key-frame. Сгенерирован
серый IDR (x264 Baseline CAVLC qp=26, 1280×720) с **переписанным
slice-заголовком** под пространство нашего SPS/PPS: `frame_num u(8)=0`,
`idr_pic_id=0`, без poc_lsb (poc_type=2), без deblock-полей
(`deblock_filter_control_present=0`), `qp_delta=−3` (сохраняет slice_qp=23
при pic_init_qp=26). Результат: FFmpeg декодирует без единой ошибки,
весь кадр — идеальный серый 128.

Техника включает два неочевидных места:

- при `deblock_idc=0` (фильтр **включён**) в заголовке следуют
  `slice_alpha_c0_offset` и `slice_beta_offset` (2×se(v)) — их пропуск
  сдвигает весь хвост данных на 2 бита;
- RBSP-эскейпинг (`00 00 03`) нужно пересчитывать после любой правки битов.

### 5.4. Почему канал 01 не играет в браузере (хронология)

Последовательность фатальных для ch01 декодеров, каждая проверена
экспериментом:

1. **WebCodecs VideoDecoder** — Chrome фаталится («Decoding error.»)
   на P-слайсах: неспецификационные intra-режимы в строке 0 макроблоков
   (`top block unavailable for requested intra mode`); FFmpeg маскирует
   это concealment'ом, WebCodecs — нет.
2. **MSE-пайплайн (jmuxer → fMP4 → `<video>`)** — тот же вердикт на уровне
   пайплайна: `PIPELINE_ERROR_DECODE: Failed to send video packet
   for decoding ... is_key_frame=0`. Это не обходится ни AUD-инъекцией,
   ни software-decode флагами.
3. **Серверный транскод FFmpeg** (decode с concealment → re-encode x264
   Baseline, AUD, IDR каждые 50 кадров) технически работает и даёт
   играбельный поток в MSE — но, как установлено (5.1), воспроизводит
   мусор второй панели. Инфраструктура оставлена в коде
   (`Ch1Transcoder.cs`) как рабочий пример серверного транскода.

### 5.5. Выводы по jmuxer (получены при отладке)

- jmuxer нарезает кадры на сэмплы **только по non-VCL NAL** (SPS/PPS/SEI/AUD)
  или `first_mb_in_slice≠0`; P-only поток с fmb=0 без AUD сливается в один
  бесконечный сэмпл → `buffer error`;
- `createBuffer` (создание SourceBuffer) выполняется один раз по событию
  `ready` ремуксера: если фид со SPS пришёл раньше `sourceopen`,
  контроллеры не создаются никогда и сегменты молча теряются;
- при `flushingTime: 0` каждое событие буфера флашится сразу
  (`onBuffer → applyAndClearBuffer`);
- «buffer error» от jmuxer — это SourceBuffer error; при опережении
  кормления над currentTime пайплайн умирает на стагнации — канал 00
  с честным темпом (duration из µs-таймстампов) работает без сбоев.

## 6. Аудио

В захватах наблюдались only-видео маркеры `NNdc`. Аудио-пакеты в AVI-нотации
выглядели бы как `NNwb` — не обнаружены. Наличие аудио не подтверждено.

## 7. Верификация

```bash
# дамп
cat toServer720.bin | timeout 20 nc 192.168.31.150 9000 > dump.bin

# извлечение канала: все байты от первого start code после маркера
# до начала следующего маркера "NNdcH264"
python3 - <<'EOF'
import re
data = open('dump.bin','rb').read()
markers = [(m.start(), m.group()[:2].decode()) for m in re.finditer(rb'[0-9][0-9]dcH264', data)]
sc = b'\x00\x00\x00\x01'
out = bytearray()
for i,(pos,ch) in enumerate(markers):
    if ch != '00': continue            # канал 00
    end = markers[i+1][0] if i+1 < len(markers) else len(data)
    k = data.find(sc, pos+24, end)
    if k >= 0: out += data[k:end]
open('ch00.h264','wb').write(bytes(out))
EOF

# проверка
ffprobe -f h264 -i ch00.h264 -show_streams
ffmpeg -f h264 -i ch00.h264 -frames:v 1 frame.jpg
```

Результат: `h264, Baseline, 704x576, yuv420p` — кадры декодируются.
