# Протокол MDVR (видеодомофон 192.168.31.150:9000)

Документ — результат реверс-инжиниринга по дампам трафика (файлы
`fromServer720*.bin`). Все смещения и размеры выведены эмпирически
и проверены декодированием через FFmpeg.

## 1. Транспорт

- TCP, порт **9000**. Соединение инициирует клиент.
- Также открыт порт **8000** — отвечает `412 Precondition Failed` на любой HTTP
  (SDK-порт, назначение не выяснялось). RTSP (554), HTTP (80) закрыты.
- TTL пакета ~61 (несколько хопов); устройство отвечает на ICMP.

## 2. Handshake

Клиент отправляет бинарный запрос **500 байт** — файл `toServer720.bin`
(снят с оригинального приложения; имя «720» отсылает к запрошенному потоку).

Hex-значимые байты (весь остальной объём — нули):

```
0000: 00 00 00 01 00 00 00 03 03 00 00 00 ...
0010: ... 00 68 00 00 00 01 00 00 00 10 00 00 00 01 00 00 00 01 ...
0028: 00 d6 9b 05 00 00 00 00 50 31 e3 02 00 00 75 00 b8 d5 9b 05 1e 55 b3 77 ...
```

После handshake сервер отвечает заголовком сессии (~0x210 байт), в котором
опознаётся строка `MDVR96NT_2_R`, поля `40 1f 00 00` (=8000, порт?),
`14 96 00 00` (=38416). Далее без остановки идёт поток видео-пакетов.

**Примечание:** при каждом новом соединении сервер продолжает слать поток
без повторной аутентификации; handshake достаточно отправить один раз.

## 3. Заголовок сессии

```
0000: 10 00 00 00 00 00 00 00 00 00 00 03 01 00 00 13 ...
0034: 04 1a 0b 13 16 39 36 1a 0b 13 16 39 36          — серийные поля
0040: 01 00 00 00 01 00 00 01 08 00 00 00 ...
0050: 40 1f 00 00 ... 14 96 00 00
0060: "MDVR96NT_2_R"                                    — модель устройства
0199: ... 01 41 00 00 40 1f 00 00 ...
```

## 4. Формат видео-пакета

Пакеты обоих каналов чередуются в общем потоке. Граница пакета —
ASCII-маркер:

```
"NNdcH264"   (8 байт)
```

где `NN` — десятичный номер канала ASCII-цифрами: `00` или `01`.
Суффикс `dcH264` — от AVI-нотации (`00dc` = «stream 00, compressed»),
т.е. поток унаследован от файлового формата AVI.

### Заголовок пакета (после маркера)

| Смещение | Размер | Тип | Значение (эмпирически) |
|---|---|---|---|
| +0 | 8 | ASCII | `NNdcH264` |
| +8 | 4 | u32 LE | размер полезной нагрузки |
| +12 | 4 | u32 LE | флаги/счётчик (`04 03 00 00` у кадров с заголовками) |
| +16 | 8 | u64 LE | **µs-таймстамп** (монотонный, устройства) |
| +24 | ~14–32 | — | служебные поля, составляют до первого start code |

### Полезная нагрузка

После переменного служебного заголовка идёт **элементарный поток H.264
в формате Annex-B** (start codes `00 00 00 01`). Границу полезной нагрузки
надёжнее всего находить поиском первого start code после +24.

Пример первого пакета канала 00:

```
30 30 64 63 48 32 36 34   "00dcH264"
7f 40 00 00               размер 0x407f
10 00 00 00               флаги
95 45 e4 70 04 03 00 00   таймстамп (µs) LE → 0x0000_0304_70e4_4595
1a 0b 13 16 0c 16         служебное
00 00 19 00 00 00         25 (fps?), нули
c0 02 40 02               704×576 LE ← размеры кадра!
00 00 00 01 67 42 00 1e 95 a8 2c 04 99   SPS (Baseline)
00 00 00 01 68 ce 3c 80               PPS
00 00 00 01 06 e5 01 2b 80            SEI
00 00 00 01 65 ...                    IDR-кадр
```

Замечание: `c0 02` = 704, `40 02` = 576 (little-endian) в заголовке канала 00.

## 5. Каналы

| Канал | Маркер | Разрешение | Частота кадров | SPS/PPS | Статус |
|---|---|---|---|---|---|
| 00 | `00dcH264` | 704×576 | **~1.25 fps** (медиана дельт 800 мс; встречаются 40–920 мс) | с каждым IDR | декодируется |
| 01 | `01dcH264` | 720p (виде 1280×720) | **25 fps** (дельты 40 мс) | **не встречаются** | не декодируется |

Таймстампы пакетов — микросекунды, монотонные, общие для каналов.
Пример дельт ch01 (мс): `40 40 39 40 41 38 39 40 …`

### Почему канал 01 не играет

1. В 8 МБ захвата не найдено ни одного SPS/PPS внутри пакетов `01dc`
   (первый NAL каждого пакета — тип 1, non-IDR slice; единственный IDR
   в захвате — на смещении 0xc6cc6 без предшествующих заголовков).
2. Синтезированные x264 SPS/PPS (1280×720 Baseline) отклоняются декодером
   (height overflow) — параметры энкодера домофона неизвестны.

Гипотезы для будущей работы:
- SPS/PPS канала 01 приходят в первом пакете сессии (до первого маркера
  `01dcH264`) либо выдаются отдельным запросом;
- заголовок сессии (0x210 байт) может содержать их в служебных полях;
- handshake, содержащий «720», возможно, выбирает только канал 01 —
  стоит поэкспериментировать с байтами запроса (другие разрешения/каналы).

## 6. Аудио

В захватах наблюдались only-видео маркеры `NNdc`. Аудио-пакеты в AVI-нотации
выглядели бы как `NNwb` — не обнаружены. Наличие аудио не подтверждено.

## 7. Верификация

```bash
# дамп
cat toServer720.bin | timeout 20 nc 192.168.31.150 9000 > dump.bin

# извлечение канала: все байты от первого start code после маркера
# до начала следующего маркера "NNdcH264"
python3 - <<'EOF'
import re
data = open('dump.bin','rb').read()
markers = [(m.start(), m.group()[:2].decode()) for m in re.finditer(rb'[0-9][0-9]dcH264', data)]
sc = b'\x00\x00\x00\x01'
out = bytearray()
for i,(pos,ch) in enumerate(markers):
    if ch != '00': continue            # канал 00
    end = markers[i+1][0] if i+1 < len(markers) else len(data)
    k = data.find(sc, pos+24, end)
    if k >= 0: out += data[k:end]
open('ch00.h264','wb').write(bytes(out))
EOF

# проверка
ffprobe -f h264 -i ch00.h264 -show_streams
ffmpeg -f h264 -i ch00.h264 -frames:v 1 frame.jpg
```

Результат: `h264, Baseline, 704x576, yuv420p` — кадры декодируются.
